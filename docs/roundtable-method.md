# 思想圆桌方法

本文档简要说明 Philophany 当前“思想圆桌”的工作方式：系统如何从用户问题选择候选哲学家，如何组成圆桌，以及后续辩论如何展开。

## 目标

思想圆桌不是“分别采访几个哲学家”，而是让一组哲学家围绕同一个问题发生有结构的思想交锋。

核心目标：

- 选出适合讨论用户问题的哲学家阵容。
- 保证阵容内部有足够差异和张力。
- 让发言者回应彼此，而不是各说各话。
- 在用户插入追问时，控制谁该回应、怎么回应。

## 输入数据

圆桌主要依赖三类数据：

1. 哲学家角色卡
   - `topics`
   - `coreConcepts`
   - `stance`
   - `summary`
   - `voice`
   - `speechPersona`
   - `exampleStyle`
   - `opening`
   - `questionHooks`

2. 哲学家关系图谱
   - `influence`
   - `tension`
   - `affinity`
   - `weight`
   - `reason`

3. 用户问题
   - 初始问题，例如“我该不该追求成功？”
   - 后续追问，例如“让尼采反驳康德”

## 第一步：解析用户问题

当用户点击“召集圆桌”时，系统先分析问题。

如果后端可用，会调用 DeepSeek 官方 API，让模型输出：

- `themes`：问题涉及的主题。
- `implicitConcepts`：隐含哲学概念。
- `tensions`：问题中的内在张力。
- `discussionNeeds`：这场圆桌需要覆盖的问题维度。它不是给哲学家贴的角色标签。
- `philosopherFit`：每位哲学家对该问题的语义适配分。
- `summary`：一句话说明系统对问题的理解，语气自然，不使用诊断式口吻或“不是……而是……”这类模板说法。

如果后端不可用，则使用本地关键词识别主题作为 fallback。

## 第二步：给每位哲学家打分

每位哲学家的选择分分成两层：先判断“是否足够相关”，再在相关候选里判断“谁更适合组成这一桌”。

```txt
relevanceScore =
  语义适配分
  + 主题匹配分
  + 核心概念匹配分
  + 问题维度覆盖分
  + 问题张力匹配分

finalScore =
  relevanceScore
  + 已选阵容差异加成
  + 小的基础加成
```

各项含义：

- 语义适配分：LLM 判断该哲学家是否适合讨论这个问题。
- 主题匹配分：用户问题主题是否命中哲学家 `topics`。
- 核心概念匹配分：隐含概念是否命中哲学家 `coreConcepts`。
- 问题维度覆盖分：该哲学家的 `topics`、`coreConcepts`、简介或语气是否覆盖这场讨论需要的关键词。这里只匹配 `discussionNeeds.needs`，不把 `label` 当作哲学家的身份标签。
- 问题张力匹配分：该哲学家是否能回应用户问题内部的冲突点，例如自由与责任、欲望与安宁、行动与怀疑。这里不是指哲学家之间的关系张力。
- 阵容差异加成：在已经足够相关的候选里，越能和已选哲学家形成差异、张力或互补，越容易被选中。

当前第一版设置了一个相关性门槛：

```txt
RELEVANCE_GATE_THRESHOLD = 2.2
```

只有 `relevanceScore >= 2.2` 的哲学家才进入候选池。多样性加成只在这个候选池内部生效，避免一个与问题关系较弱、但和已选成员差异很大的人被硬推上桌。

`discussionNeeds` 只影响选人，不会传入发言 prompt。它回答的是“这个问题需要覆盖哪些维度”，不是“某个哲学家应该扮演什么角色”。例如“质疑前提”可以说明这场讨论需要有人检查问题预设，但不会把某位哲学家固定成“怀疑论者”。

## 第三步：逐个选择圆桌成员

圆桌不是一次性选最高分的五个人，而是逐个选择。

流程：

```txt
selected = []

while selected.length < 5:
    给所有未选哲学家计算 relevanceScore
    candidatePool = relevanceScore >= 2.2 的候选

    如果 candidatePool 不为空:
        在 candidatePool 内计算 finalScore
        finalScore 最高者加入 selected

    如果 candidatePool 为空:
        回退到 relevanceScore 最高者加入 selected
```

这样做的原因是：每选入一位哲学家，后续候选的分数会受到阵容差异影响。
但阵容差异不是入场券，只是场内排序规则。相关性先决定“能不能进候选池”，多样性再决定“在候选池里谁更适合补上这一席”。

例如：

- 如果问题本身足够涉及自由、价值重估或主体困境，且已选康德，尼采可能因为 `tension` 加分。
- 如果问题本身足够涉及礼、自然、社会规范或自我安顿，且已选孔子，庄子可能因为儒道张力加分。
- 如果问题本身足够涉及知识、德性或追问方式，且已选苏格拉底，柏拉图可能因为影响关系或问题亲缘加分。

目标不是机械选出五个单项最高分的人，也不是为了多样性牺牲相关性，而是选出一个既切题、又能讨论起来的组合。

## 第四步：展示推荐理由

每位被推荐的哲学家会显示若干理由，例如：

- 语义适配。
- 匹配主题。
- 命中隐含概念。
- 覆盖某些问题维度。
- 与已选哲学家存在影响、张力或亲缘关系。

推荐理由用于帮助用户理解“为什么是这几个人”，也方便用户手动替换阵容。

## 第五步：生成第一轮圆桌

用户点“下一位”时，前端把以下上下文发给后端：

- 用户问题。
- 当前参与者。
- 每位参与者的角色卡。
- 当前阵容内部的图谱关系。
- 最近对话历史。
- 当前动作：`opening_step`。
- 当前应该发言的哲学家 id。

后端 prompt 的核心规则：

- 第一轮不是一次性生成五条发言，而是用户每点一次“下一位”，只生成一位哲学家的发言。
- 第一位哲学家先提出初始立场。
- 后续哲学家必须回应已经可见的前文中任意一位哲学家的具体观点。
- 不要求只回应上一位。
- 发言方式由哲学家自主选择，可以是赞同、反驳、澄清、补充、追问或建议。
- 不允许只是介绍自己的思想。
- 不允许伪造名言、页码、章节或具体引文。

在旧的 sequential 回退模式中，第一轮仍按阵容顺序推进，但用户可以在任意两位哲学家之间停下来追问。每位哲学家说完后，后台会更新 `discussionState`，下一位只能基于已经出现的内容继续讨论，而不能预设后面的人会说什么。

### 实验性 LLM 动态调度

当前试验版默认开启 `LLM 动态调度`。它不再把第一轮固定理解成“阵容中每个人按顺序说一遍”，而是在用户每次点击“下一位/继续讨论”时，先调用 `/api/next-speaker` 让 DeepSeek 官方 API 判断谁最有理由接着说话，然后再调用 `/api/chat` 生成这位哲学家的具体发言。

调度器只决定下一位是谁，不生成发言内容。它参考：

- 上一条发言是否点名、反驳或隐性挑战了某位哲学家。
- 参与者之间的 `influence`、`tension`、`affinity` 关系。
- `discussionState.unresolvedTensions` 与 `claimsOnTable`。
- 用户原问题和当前追问。
- 沉默补偿：长期没发言但仍相关的人会被提高优先级。
- 最近发言惩罚：刚连续发言的人会被压低优先级，除非被直接挑战。

这让第一轮之后可以自然继续推进：用户不追问也能继续看圆桌围绕未解张力发展；用户插入追问时，系统优先处理追问，非点名追问之后也可以回到动态推进。

回退方式保留在前端本地开关里。浏览器控制台执行下面命令后刷新页面，就会回到旧的 sequential 顺序调度：

```js
localStorage.setItem("philophany.roundScheduler", "sequential")
```

恢复 LLM 动态调度：

```js
localStorage.removeItem("philophany.roundScheduler")
```

也就是说，新机制可以试用审查；如果效果不好，旧的逐位调度代码仍然保留。

## 第六步：辩论逻辑

圆桌发言遵循一个基本协议：

```txt
每条发言 = 回应用户问题 + 回应某个此前观点
```

发言者可以自主选择回应方式：

- 反驳：先准确复述对方强版本，再指出分歧。
- 赞同：说明赞同哪一点，并补充自己的理由。
- 澄清：澄清概念、前提或问题边界。
- 补充：从自己的传统或核心概念扩展讨论。
- 追问：把问题推向更深一层。
- 建议：把哲学分歧转成用户可执行的下一步判断。

为了避免更隐蔽的“概念同化”，任何发言只要提及另一位哲学家的观点，都必须保留对方自己的核心概念、问题意识或关系语境，不能直接把对方立场改写成发言者自己的概念框架。

例如，康德不能把萨特的自由直接说成“自律的另一种表达”；王阳明不能把庄子的逍遥直接说成“良知自然流行”。如果发言者确实要转译或类比，必须明确说明这是自己的解释，而不是对方原本的说法。

这条规则不只适用于反驳，也适用于赞同、澄清、补充、追问和建议。

系统不显式给用户一个“反驳/赞同按钮”。这些回应方式由模型根据角色、关系和上下文自行选择。

### 发言人格

为了让圆桌更适合对哲学感兴趣的普通用户，每位哲学家可以带一个 `speechPersona`。它不是哲学关系数据，也不会改变图谱；它只描述这位哲学家在圆桌里怎么说话。

`speechPersona` 包含：

- 脾气。
- 惯用动作。
- 遇到反对时的反应。
- 句子节奏。
- 容易过火的风险。
- 1 到 2 条样例句。

允许的发言动作包括：打断、反问、拒答、重框、挑衅、缓和、翻译成人话。

安全边界：

- 可以锋利，但不能人身攻击用户。
- 可以不礼貌，但不能辱骂。
- 可以拒绝问题，但必须给出更好的问法。
- 可以打断别人，但不能歪曲别人。

`speechPersona` 可以由 DeepSeek 官方 API 生成候选稿，但必须经过人工审核。流程是：

```txt
reviewed_philosopher_cards.json
  -> generate_speech_personas.py
  -> reviewed_speech_personas.json
  -> 人工审核 humanDecision
  -> merge_speech_personas.py
  -> reviewed_philosopher_cards.json
  -> assemble_data_js.py
  -> data.js
```

### 例子协议

为了让抽象分歧更容易被普通用户感知，每位哲学家可以带一个 `exampleStyle`。它描述这位哲学家适不适合举例、偏好哪种例子，以及是否适合围绕别人给出的例子继续争论。

`exampleStyle` 包含：

- `mode`：例子形态，例如对话处境、生活场景、寓言、语言游戏、内在经验或准则测试。
- `frequency`：使用频率，分为 `high`、`medium`、`low`。
- `canDebateOnExample`：是否适合直接讨论别人提出的例子。
- `preferredExampleForms`：偏好的例子类型。
- `avoidExampleForms`：应避免的例子类型。
- `signatureExample`：这位哲学家最自然的例子入口。

例子协议：

- 高频或中频哲学家可以主动使用一个短例子、比喻或反例，让观点更可感。
- 低频哲学家不必强行举例，但可以分析别人例子的结构。
- 如果上一条发言包含具体例子，下一位哲学家应优先围绕这个例子推进，而不是把它当装饰。
- 后续发言可以用同一个例子给出不同结论，也可以提出反例、指出例子预设，或说明这个例子为什么误导。
- 例子不能替代论证，不能编造具体历史轶事、真实人物故事或名言，也不能把讨论从用户原问题带走。

`exampleStyle` 由 DeepSeek 官方 API 生成候选稿，但和 `speechPersona` 一样必须经过人工审核。流程是：

```txt
reviewed_philosopher_cards.json
  -> generate_example_styles.py
  -> reviewed_example_styles.json
  -> 人工审核 humanDecision
  -> merge_example_styles.py
  -> reviewed_philosopher_cards.json
  -> assemble_data_js.py
  -> data.js
```

## 后台讨论状态追踪

圆桌每生成一轮内容后，系统会在后台更新一个 `discussionState`。它不是 UI 功能，不在页面上展示；它只是给下一次后端 prompt 使用的主持人笔记。

当前状态只记录四类信息：

- `claimsOnTable`：已经进入讨论、仍然影响后续发言的核心主张。
- `unresolvedTensions`：已经出现但还没有真正交锋的分歧。
- `unquestionedAssumptions`：各方默认但尚未被追问的前提。
- `drift`：讨论是否偏离用户原问题。

`claimsOnTable` 中每条主张包含：

```json
{
  "claim": "一句话概括已经出现的核心主张",
  "speaker": "kant",
  "status": "unanswered | challenged | clarified | repeated",
  "needsFollowUp": true
}
```

这个状态追踪器只回答“讨论已经发生了什么、还有哪些东西悬着”。它不使用 nextBestMove，不决定下一轮该挑战、总结还是澄清，也不规定哪个哲学家必须怎么说。这样可以减少重复和跑题，同时避免后台机制过度导演讨论。

## 第七步：用户插入追问

用户可以在任意时刻插入问题。

追问分两类：

### 点名追问

如果用户只点名了一位哲学家，例如：

```txt
让康德解释一下为什么义务比幸福重要
```

系统会只允许康德回应。

也可以用 `@` 明确指定发言者，例如：

```txt
@庄子 什么是逍遥
@庄子 对 @孔子 反驳
@庄子@孔子 你们对成功有什么想法
```

默认规则是：第一个可识别的 `@` 决定谁发言；后续 `@` 保留为回应对象。所以上面第二句会让庄子发言，并把孔子作为被回应或反驳的对象。

如果多个 `@` 连在开头，或者问题里出现“你们 / 二位 / 两位 / 各自 / 分别 / 都”等多人询问信号，系统会把这些哲学家组成逐位回应队列。上面第三句会先让庄子回应，之后用户点“下一位回应”时再让孔子回应；仍然不是一次性生成多条。

点名追问直接回答用户问题，不会为了延续圆桌而强行回应前文中的其他哲学家。只有当用户明确要求比较、反驳或回应某人时，系统才会让被点名者连接对应前文。

判断方式包括：

- “@某某”
- “让某某”
- “请某某”
- “问某某”
- “追问某某”
- “针对某某”
- “某某怎么看”
- “某某怎么回应”
- “某某解释”
- “某某回答”

### 非点名追问

如果用户没有指定单一哲学家，例如：

```txt
那我到底应该怎么行动？
```

追问后也按逐位回应推进，不是一次性让所有哲学家同时回应。用户提交追问后，系统先生成一位哲学家的回应；如果还想听其他人继续回应，可以继续点“下一位回应”。

在动态调度开启时，非点名追问会进入一个临时追问进程。每次继续回应时，调度器会根据用户追问、最近对话、未解决张力、沉默补偿和图谱关系选择下一位发言者。这个进程会在两种情况下结束：

- 调度器返回 `shouldContinue: false`，表示这轮追问已经暂告一段落。
- 追问回应达到上限，目前是 `DYNAMIC_ROUND_MAX_TURNS = 7`。

结束后，下一次点击继续讨论会回到原始问题的主线圆桌。

如果用户不想等系统判断，也可以在追问进程中点击“回到原问题”。这个按钮会立即清空当前追问进程；下一次点击继续讨论时，系统重新围绕原始问题调度下一位哲学家。

顺序回退模式下，非点名追问按当前圆桌顺序推进，但会从最近发言者之后的人开始，避免同一个人刚说完又立刻抢先回应。点名追问仍然只让被点名的人回应一次，不自动开启多人回应队列。

## 第八步：总结分歧

用户点击总结时，系统只生成一条 `system` 总结。

总结目标：

- 不替用户做最终选择。
- 画出核心分歧。
- 区分哪些分歧仍是开放问题。
- 指出哪些立场在当前讨论中论证更强或更弱。
- 点出可能的实践风险或规范风险。
- 给用户一个下一步最该澄清的判断标准。

总结不是裁判判决，但也不是廉价中立。它要帮助用户看清讨论的真实状态：哪些问题还需要继续想，哪些理由已经暴露了漏洞，哪些观点如果付诸实践可能带来伤害、压迫、逃避责任或自我欺骗。

## 本地 fallback

如果 DeepSeek 官方 API 调用失败，系统会用本地演示逻辑生成内容。

本地逻辑较简单：

- 第一轮使用角色卡里的 `opening`。
- 用户说“反驳”时，找一个立场距离较远或存在 `tension` 的对手。
- 用户说“解释”时，解释该哲学家的核心概念。
- 用户提到王阳明、知行合一、良知时，会优先让王阳明回应。

本地 fallback 只保证产品可演示，不代表正式圆桌质量。

## 当前方法的边界

当前圆桌方法已经能做到：

- 根据问题自动推荐阵容。
- 用图谱关系增加阵容张力。
- 让第一轮不再各说各话。
- 支持点名追问和非点名追问。
- 禁止伪造具体引文。
- 后台已经能追踪核心主张、未解决张力、未追问前提和跑题情况。
- 这个后台追踪器目前只作为 prompt 背景，不会自动决定下一步讨论动作。

仍可改进：

- 让每条发言显式记录回应对象。
- 区分历史影响、问题亲缘、比较张力在辩论中的不同作用。
- 让用户能调节圆桌风格，例如更激烈、更实用、更学术或更温和。

## 一句话总结

Philophany 的思想圆桌方法可以概括为：

```txt
先用问题理解和图谱关系选出有适配、有差异、有张力的阵容，
再用严格的圆桌协议要求每位哲学家回应用户问题和彼此前文，
最后让用户通过追问改变讨论方向，而不是被动观看固定剧本。
```
